# Deployment

Supported target: Ubuntu 22.04 or 24.04, x86_64 or aarch64, at least 1 CPU, 1.75 GiB RAM, 5 GiB free disk, Docker with Compose plugin, and inbound ports 80/443. The intended production VPS is **1 CPU, about 2 GB RAM, 4 GB swap, and about 24 GB disk**; load testing on that profile remains required. Install `curl`, `dnsutils`, `iproute2`, `openssl`, and `cron` beforehand; ensure the cron service is running. Point exactly one A record to the VPS IPv4; if an AAAA record exists, point it to the VPS IPv6.

1. Upload this repository to the VPS and run `chmod +x install.sh update.sh backup.sh restore.sh schedule-backups.sh`.
2. Run `./install.sh`. It checks prerequisites, DNS, ports, Telegram network access, then prompts for domain, bot token, admin Telegram ID, and optional OpenAI key.
3. It creates a private `.env`, generates a Caddy configuration, starts containers, and validates `https://DOMAIN/api/health`.
4. In BotFather, configure the bot's menu button Web App URL as `https://DOMAIN/app/`. The bot now presents a private keyboard after language selection and Terms acceptance; keep only `/start` and `/help` as public command hints.
5. Message `/panel` to the bot from the configured admin account. Enter the code at `https://DOMAIN/panel/`.
6. Follow [INTEGRATIONS.md](INTEGRATIONS.md) to add Sanaei panels, discover and map inbounds, configure products and payment methods, and verify real provisioning. Do not accept customers before live payment, provisioning, renewal, and expiry checks pass.

The `.env` variables include `DOMAIN`, `BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, `POSTGRES_PASSWORD`, `SESSION_SECRET`, `PANEL_ENCRYPTION_KEY`, `BACKUP_ENCRYPTION_KEY`, optional `OPENAI_API_KEY` and `OPENAI_MODEL`, optional NOWPayments credentials, and optional `OPS_CHAT_ID` plus `OPS_TOPIC_*` identifiers. `DATABASE_URL` is constructed inside Compose. The installer generates the encryption keys. Keep an offline copy of `BACKUP_ENCRYPTION_KEY`; losing it makes encrypted backups unreadable. Sanaei credentials are added after installation through the Admin Panel. New private receipts live in the named `private_data` volume and are included in encrypted backups.

After this release's update tooling is installed on the VPS, future releases can be one file: run `python -m alart.release pack alart-release.tar.gz` on the development machine, transfer the archive, and run `./update.sh alart-release.tar.gz` on the VPS. This path creates an encrypted backup of the running source and database before applying the archive. It then builds, starts services, checks HTTPS health, and records `VERSION` in `.deployed-version`. An older installation that lacks `alart.release` and `alart.backup_crypto` needs a one-time deployment of this source tree first; its old update script cannot consume this archive format. The new workflow does not fetch code or roll back automatically. `.env`, Caddyfile, and Docker volumes are preserved. The old backup needs the offline `BACKUP_ENCRYPTION_KEY` to restore. Running `./update.sh` with no archive remains available when source was already staged; preserve the previous release separately in that case. See `OPERATIONS.md` for restore.

For topic logging, create a private supergroup and the Purchases, Payments, Wallet, Referral, Users, Provisioning, Errors, Security, Backup, and System topics. Add the bot with posting permission. Send `/topicid` as the configured admin inside each topic to read its numeric chat/topic IDs. Put `OPS_CHAT_ID` and the corresponding `OPS_TOPIC_*` values in `.env`, then restart with `docker compose up -d --force-recreate api worker`. Do not put the bot token or customer configuration in a topic message.
